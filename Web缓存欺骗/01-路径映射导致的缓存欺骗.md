# Lab：Exploiting path mapping for web cache deception

> 难度：APPRENTICE ｜ 分类：Web 缓存欺骗 ｜ 状态：📖 解析（待本人实操验证）
> 官方页面：https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-path-mapping

## 一、漏洞原理

缓存服务器和源站对**同一个 URL 路径的解释方式不一致**，攻击者利用这个差异，让缓存把含敏感信息的动态响应当成静态资源存下来，随后自己请求同一 URL 就能读到别人的数据。

以路径映射差异为例：

```
http://example.com/user/123/profile/wcd.css
```

- 源站用 REST 风格映射：把它当作 `/user/123/profile` 端点，忽略末尾的 `wcd.css`，返回用户 123 的资料；
- 缓存用传统文件映射：把它看成 `/user/123/profile/` 目录下名为 `wcd.css` 的文件，命中"路径以 `.css` 结尾就缓存"的规则。

注意区分：**缓存欺骗**是骗缓存存下私密内容（本 lab）；**缓存投毒**是操纵缓存键把恶意内容注入给别人，两者方向相反。

## 二、标准利用链

1. 找一个返回敏感信息的动态端点，优先 `GET` / `HEAD` / `OPTIONS`（会改变源站状态的请求一般不被缓存）；Burp 里看原始响应，有些敏感字段不显示在渲染页面上；
2. 在路径后加一段任意字符，如 `/my-account` → `/my-account/foo`：若仍返回同样的敏感数据，说明源站抽象了路径、忽略附加段；
3. 再加静态扩展名：`/my-account/foo.js`（也可试 `.css` / `.ico` / `.exe`）。观察 `X-Cache` 头——首次 `miss`、再请求变 `hit`，或 `Cache-Control: public, max-age>0`，即确认响应被缓存；
4. 构造该 URL 诱导受害者访问，随后自己请求同一 URL 读取缓存中的受害者数据。官方提醒：**不要在浏览器里直接做最后这步**，未带会话时应用可能重定向或清空本地数据，掩盖漏洞；
5. 测试期间每次请求换一个查询串（cache buster），否则拿到的可能是上一次的缓存结果。

## 四、防御视角

核心是**消除缓存与源站的解析差异**：

- 缓存规则不要只靠"路径以 `.js`/`.css` 结尾"这种宽匹配，改为只缓存明确的静态目录（`/static`、`/assets`）；
- 动态、含用户数据的响应统一发 `Cache-Control: no-store` / `private`，让缓存层没有机会存；
- 源站路由与缓存规则对分隔符、路径规范化、路径映射的处理要一致；CDN 与后端框架升级后需重新核对这套假设。

## 五、一句话复盘

"Web 缓存欺骗利用的是缓存和源站对同一 URL 路径的解释差异：给动态端点挂一个 `.js` 后缀，源站忽略它照常返回敏感数据，缓存却把它当静态文件存下来，攻击者再请求同一 URL 就能读到受害者的响应。防御上要把缓存规则收窄到明确的静态目录，并给动态响应加 no-store。"
